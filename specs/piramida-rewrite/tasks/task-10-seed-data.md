## Description

Идемпотентный скрипт `scripts/seed.ts` (`pnpm seed`) заполняет пустую БД первичными данными: залы, тарифы аренды в минутах операционных суток, доп. услуги, штрафы, акции, календарь турниров 2026, всё меню клуба (категории, позиции, варианты, общие сетки цен, добавки), два примера банкетных сетов, настройки сайта, тексты 4 вкладок «Услуги», пустые галереи и версию 1 юридических документов (черновики с плейсхолдерами). Источники: распознанные прайсы `specs/piramida-rewrite/data/res-transcription.md` и факты старого сайта `specs/piramida-rewrite/data/legacy-notes.md`. Распарсенные данные лежат типизированными TS-модулями в `scripts/seed-data/*.ts` — по одному на домен, чтобы их можно было ревьюить. Владелец клуба правит данные в админке; seed нужен для старта и staging.

### Implementation Steps

1. Прочитать `src/lib/schema/*.ts`, `src/lib/db.ts`, `src/lib/slug.ts`, `src/lib/dates.ts`, а также **целиком** `specs/piramida-rewrite/data/res-transcription.md` (разделы 1–5) и `data/legacy-notes.md`.
2. Принципы seed:
   - Данные живут в `scripts/seed-data/*.ts` как типизированные константы (без логики БД). `scripts/seed.ts` только импортирует их и пишет в БД.
   - Импорты в скриптах относительные (`../src/lib/db`, `../src/lib/schema`), `@/` не использовать.
   - **Идемпотентность = «создать, если нет»**: каждая сущность ищется по естественному ключу (slug, code, `key`, `(type, version)`, `(categoryId, name)` и т.п.); найдена — не изменяется (повторный запуск **не затирает правки админа**); не найдена — вставляется. Ничего не удаляется. Транзакция на каждый домен.
   - Для сущностей без slug естественные ключи: тариф — `(hallId, label, startMin, endMin, audience, daysOfWeek)`; доп. услуга и штраф — `(name)` / `(kind, name)`; сетка цен — `(name)`; уровень сетки — `(groupId, label)`; позиция меню — `(categoryId, name)`; вариант — `(itemId, sortOrder)`; добавка — `(name)`; серия турниров — `slug`; турнир — `slug`; акция — `slug`; услуга — `key`; галерея — `key`; юр. документ — `(type, version)`.
   - В конце скрипт печатает счётчики «создано / уже было» по доменам и сверочные итоги (30 турниров, 56 штрафов = 33 + 23, число позиций меню ≈ 259, у каждой позиции без сетки цен ≥ 1 вариант) и завершается `await queryClient.end()` (`queryClient` экспортируется из `src/lib/db.ts`, задача 03).
   - Порядок: настройки → залы → тарифы → доп. услуги → штрафы → серии → турниры → меню (price groups → категории → позиции/варианты → добавки) → акции (нужна категория «Крепкие напитки») → сеты (нужны варианты позиций) → услуги → галереи → юр. документы.
   - ID и коды: UUID генерирует БД (`defaultRandom`); `code` — `nanoCode()` из task 06 (при коллизии unique — повторить) для **каждой** строки `menuItems`, `menuItemVariants`, `banquetSets` и `priceGroupTiers`. Код генерируется только при вставке; у найденной по естественному ключу строки существующий `code` сохраняется (коды попадают в URL калькулятора, их нельзя менять при повторном запуске).
3. Если схема не позволяет разместить какое-то поле данных (например, нет колонки `description` у `services`), не придумывать колонки: положить текст в ближайшее допустимое поле и перечислить это в отчёте.

### 3.4 Меню (`menu.ts`) — самая объёмная часть

Источник — раздел 4 транскрипции (страницы 1–19) целиком; ничего не пропускать и **не придумывать**. Модуль описывает дерево данными, а не SQL. Рекомендуемые типы (`types.ts`):

```ts
type Unit = "g" | "ml" | "l" | "pcs"
type SeedVariant = { label?: string; amount?: number; unit?: Unit; price: number }
type SeedItem = {
  name: string
  description?: string        // состав / описание
```
